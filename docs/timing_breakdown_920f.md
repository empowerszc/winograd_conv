# 920F 上 Winograd F(4,4) 的步耗时拆解与并行效率分析

> **日期**：2026-08-11
> **数据来源**：`shapes/conv_all.csv`（59 个 shape），华为鲲鹏 920F（SVE-512、无 L3、768KB L2/核），`USE_OPENBLAS` 构建。
> **测量方式**：`bench_winograd --timing`（步耗时拆解）+ `bench_winograd --threads 1,16`（并行效率），warmup=10 / repeats=50，best-of。
>
> **结论前置（TL;DR）**：
> 1. `--timing` 模式在 2026-08-11 之前存在两个工具缺陷，导致早期拆解数据不可信（见 §2）。修复后本文件的成分分析是可信的。
> 2. 修正后，**GEMM 是第一大头但不是绝对大头**：多数 shape 约 33-50%，小图深通道 case 可达 74%；其余是变换 + 数据搬移。
> 3. **小 GEMM 效率崩塌**是「小图深通道 GEMM 占比高」的机制：4-tile 的 GEMM 只跑 ~10 GFLOPS（大 GEMM 是 140 GFLOPS）。
> 4. **Weight transform 是最便宜的优化目标**：小图深通道时占 30-54%，且每次调用都在重算同一个 V —— 跨调用缓存 V 即可去掉。
> 5. **并行效率 `(T1/16)/T16` 为 0.46-0.83**：16 线程只拿到 7-13×，净并行开销占 T16 的 20-42%。粗粒度 OpenMP 并不免费。

## 1. 测量方法：S / T1 / T16 三个量

两条命令在 920F 上运行：

```bash
# 命令 1 —— 步耗时拆解：返回每个 shape 的 S（timing Total）
./build/bench_winograd --timing --threads 16 --sve --nhwc shapes/conv_all.csv

# 命令 2 —— 并行扩展：返回每个 shape 的 T1、T16（真实路径 wall time）
./build/bench_winograd --sve --nhwc --threads 1,16 shapes/conv_all.csv
```

三个量的定义：

| 量 | 来源 | 含义 |
|---|---|---|
| **S** | 命令 1 的 `Total(ms)` | `run_with_timing`（串行复刻版）跑完整个 conv 的时间，并按 8 步拆分 |
| **T1** | 命令 2，1 线程列 | 真实路径 `winograd_convolution_nhwc_core` 在 1 线程下的 wall time |
| **T16** | 命令 2，16 线程列 | 同一真实路径在 16 线程下的 wall time |

关系与用途：

- `T1/16`：真实路径「理想线性扩展到 16 线程」的参照。
- 并行效率 `eff = (T1/16) / T16`：离 1 越远，调度 + 竞争开销越大。
- 净并行开销 `T16 − T1/16` ≈ 正开销（barrier 等待 + 动态调度 + 负载不均 + cache 竞争）− 负开销（Phase3 `nowait` 的 batch 间重叠）。
- `S − T1`：timing 复刻相对真实路径的偏差（见 §5）。

`--timing` 是**串行复刻版**，8 步为：Weight（权重变换）、TileExt（输入 tile 提取）、InXform（输入变换）、InScat（散到 U）、GEMM、OutGath（从 M 收集）、OutXform（输出变换）、OutWrite（写回）。

## 2. 工具修复：为什么早期的 timing 数据不可信

2026-08-11 修复了 `run_with_timing`（`bench_winograd.cpp` / `profile_case.cpp` 同步）的两个问题。**修复前的 timing 拆解数据不可用于结论。**

### 2.1 GEMM 只算了 1/N 的工作量（commit 4dea5c9）

修复前 `run_with_timing` 的结构是：

```
for n in 0..N:  输入变换 → 散到 U        // U 每次被覆盖，最后只剩 batch N-1 的数据
GEMM: 36 个 gemm(U, V)                    // 只跑了 1 个 batch 的量！
for n in 0..N:  从 M_buf 收集 → 输出变换   // M_buf 只有最后 1 个 batch 的结果
```

真实路径是 **per-batch** 的（输入 → GEMM → 输出），GEMM 实际跑 **N×36** 次。修复前 timing 的 GEMM 少算 N 倍，导致：

- **GEMM 占比被压低**：N=4 时真实约 40-53%，打印却只有 11-19%；
- **S 低估真实串行耗时**：对 N>1 全部出现 `T1 > S`（真实 1 线程反而比 timing 复刻慢）——与「复刻版更慢」的直觉相反。

修复：把 GEMM 挪进 batch 循环，per-batch 输入 → GEMM → 输出，与真实路径同构，GEMM 计时跨 batch 累加。

### 2.2 OpenBLAS 未钉到 1 线程（commit 0c45558）

真实路径在 OpenMP 区域前 `openblas_set_num_threads(1)`；但 `run_with_timing` 直接调 `winograd_gemm → cblas_sgemm` 时**没有钉**，OpenBLAS 用默认线程数（920F 上全核），GEMM 被 OpenBLAS 自己多线程 → 测出的 GEMM 比真实路径快。已在两个工具的 `run_with_timing` 开头补同样的钉扎。

### 2.3 修复前后对比（同一 shape）

| row | shape | 指标 | 修复前 | 修复后 |
|---|---|---|---|---|
| 0 | 4,192,40,40,192 | GEMM(ms) | 1.89 | **7.55**（≈×4） |
| 0 | 4,192,40,40,192 | S Total(ms) | 16.58 | **22.26** |
| 58 | 4,384,160,160,384 | GEMM(ms) | 63.41 | **253.00**（≈×4） |
| 20 | 1,2048,7,7,512（N=1） | GEMM(ms) | 34.13 | 33.96（不变，符合预期） |

## 3. 步耗时成分（修正后）

### 3.1 代表 shape 的 8 步拆解

### 3.2 三种形态

1. **小图深通道 → GEMM + Weight 垄断（97-99%）**：行 15/16/20/28/29/30/46。7×7、14×14、IC/OC≥512 时，GEMM 与 weight transform 合计占掉几乎所有时间。
2. **均衡（多数真实 CNN shape）→ GEMM ~33-50%，变换 + 数据搬移另一半**：行 0/2/22/24/53/54/57/58 等。
3. **大图浅通道 → 变换主导**：行 31/33（如 16 通道 224²），GEMM 仅 11%，InXform / OutXform / TileExt 是大头。

### 3.3 机制：小 GEMM 效率崩塌

GEMM 占比高的小图 case，不是「算得多」，而是「**跑得极低效**」。用 timing 的 GEMM 耗时反推单线程 GEMM 吞吐：

| shape | tiles | 单 GEMM 规模 (n×OC×IC) | GEMM 吞吐 |
|---|---|---|---|
| 4,192,40,40,192 | 100 | 100×192×192 | **140 GFLOPS** |
| 4,384,160,160,384 | 1600 | 1600×384×384 | 134 GFLOPS |
| 4,512,7,7,512 | 4 | 4×512×512 | **10.3 GFLOPS**（峰值的 ~7%） |

OpenBLAS 的 `cblas_sgemm` 在 4×512×512 这种极小矩阵上，单次调用开销 + 分块失效 → 只有 ~7% 的核效率。这是小图 case 里 GEMM 优化的主战场（改用 arm_gemm 或手写 4-tile kernel）。

### 3.4 Weight transform：缓存 V 是最高性价比优化

Weight 只跟 IC×OC 有关、不随图像摊薄，且**每次调用都在重算同一个 V**：

| shape | Weight 占比 |
|---|---|
| 1,512,7,7,512 | **54.7%** |
| 1,2048,7,7,512 | **49.0%** |
| 1,256,14,14,256 | **49.5%** |
| 4,384,160,160,384 | 0.7%（可忽略） |

真实部署权重固定 → 跨调用缓存 V（权重变换只做一次），能直接拿掉小图深通道 case 里 30-54% 的固定开销。

## 4. 并行效率：16 线程扩展

`eff = (T1/16) / T16`，speedup = `T1/T16`（理想 16×）。

| row | shape | T1(ms) | T16(ms) | T1/16(ms) | **eff** | 16线程倍率 |
|---|---|---|---|---|---|---|
| 0 | 4,192,40,40,192 | 17.55 | 1.905 | 1.097 | **0.58** | 9.2× |
| 4 | 4,384,80,80,96 | 74.30 | 5.876 | 4.64 | **0.79** | 12.6× |
| 20 | 1,2048,7,7,512 | 59.24 | 5.562 | 3.70 | **0.67** | 10.6× |
| 24 | 4,128,112,112,128 | 69.72 | 5.583 | 4.36 | **0.78** | 12.5× |
| 39 | 1,8,16,16,8 | 0.073 | 0.035 | 0.005 | **0.13** | 2.1× |
| 54 | 4,384,80,80,384 | 141.67 | 11.487 | 8.85 | **0.77** | 12.3× |
| 58 | 4,384,160,160,384 | 498.69 | 38.692 | 31.17 | **0.81** | 12.9× |
| 33 | 1,16,224,224,16 | 11.44 | 0.912 | 0.715 | **0.78** | 12.5× |

规律：

- eff 随 shape 增大而提高：小 shape ~0.46-0.58，大 shape ~0.78-0.83；微 shape（行 39）只有 0.13（纯固定开销）。
- 净并行开销 `T16 − T1/16` 占 T16 的 **20-42%**，小 shape 占比更大（行 0 占 42%，行 58 占 19%）。
- 16 线程对真实负载拿到 **7-13×**，不到理想的 16×。

含义：**自己这套粗粒度 OpenMP 并不免费**。docs §4.2「我们调度比 NEScheduler 便宜」要成立，需要配 oneDNN 同 shape 的线程扩展曲线做对照，光看自己这组数不够。

## 5. S vs T1：timing 复刻的残差

修复后 `S > T1` 对所有 shape 成立（timing 复刻做了 N×GEMM + 逐 tile 清零 + 每调用分配，比真实 1 线程路径重）。残差 `S−T1`：

| row | S(ms) | T1(ms) | 残差 (ms) | 残差/S |
|---|---|---|---|---|
| 0 | 22.26 | 17.55 | 4.7 | **27%** |
| 54 | 157.89 | 141.67 | 16.2 | 11% |
| 58 | 526.63 | 498.69 | 27.9 | 5.6% |

残差来源：timing 复刻的逐 tile 清零（`d_tile`/`U_tile`/`M_tile`/`f_tile` 的 `std::fill(0)`，行 58 约 1.2GB 的 fill 流量）+ 每调用 `std::vector` 分配 + 零初始化 V/U/M_buf。

**使用建议**：`--timing` 的**占比结构**（GEMM 33-50% 等）可信；大 shape 的 S 绝对值约高估 5-10%，小 shape 高估 ~27%（固定开销占比大）。绝对耗时以 T1（真实路径 1 线程）为准。

## 6. 测量噪声与可靠性

同一 shape 在 CSV 里出现两次（行 0 = Case 0 与行 49 = tiles×IC 网格交点，都是 4,192,40,40,192）：

| 步 | 行 0 | 行 49 | 差异 |
|---|---|---|---|
| S Total | 22.26 | 18.36 | **21%** |
| GEMM | 7.55 | 7.32 | 3%（**稳定**） |
| InScat | 1.51 | 2.50 | **65%** |
| Weight | 1.82 | 0.97 | **88%** |

- **噪声集中在内存步**（InScat/OutGath/TileExt）和 Weight，**GEMM 是稳定列**。
- 行 0 是进程内第一个 shape，冷启动使其 S 系统性偏高。timing 模式虽取 best-of-50，但 S 仍有显著 run 内漂移，S 级结论要谨慎。

---

## 7. 结论与建议

1. `--timing` 修复后能给出真实成分：**GEMM 是第一大头，但只有小图深通道 case 到 74%，多数 shape 是 GEMM 与变换/数据搬移五五开**。
2. 两个高性价比优化方向：
   - **缓存 V（weight transform 跨调用复用）**：小图深通道立省 30-54%，改动最小、收益最直接；
   - **小 GEMM 换 kernel**（arm_gemm / 手写 4-tile kernel 替代 OpenBLAS）：行 16/28/46 的 GEMM 只有 ~10 GFLOPS，峰值的 7%。
3. 并行扩展到 16 线程拿 7-13×，净开销 20-42%；与 oneDNN 对照时务必同 threads 画扩展曲线，才能归因「工程层 vs 调度层」。
