# SME F32F32 FMOPA GEMM 内核（实验后端）

> **状态**：已实现、已验证、已提交（commit `6e7639e`），默认关闭，`WINO_GEMM=sme` 启用。
> **位置**：`src/winograd_conv.cpp` → `namespace wino_sme`（846–1025 行）。
> **适用平台**：带 `smef32f32` 的 Armv9（鲲鹏 920F / 本机 608 核毕昇环境），SVE-512（VL=16 float）。
> **一句话**：用 SME 的 `fmopa` 外积累加指令替代 `cblas_sgemm`，把 Winograd 的 36 个小 GEMM
> 直接映射到 ZA 二维累加器上，**drain 出来的 64 B 切片正好是 M_buf 的一行 16 个 OC**，
> 不需要任何后置换。

## 1. 动机：Winograd 的 GEMM 形态对通用 BLAS 不友好

F(4,4,3,3) 把一次卷积拆成 **36 个互相独立的小 GEMM**：

```
M[ts][tile][oc] = Σ_ic U[ts][tile][ic] · V[ts][oc][ic]
                   M = n_tiles, N = OC, K = IC, ts = 0..35
```

| 特征 | 数值（以 59 形状集为例） | 对通用 GEMM 的影响 |
|---|---|---|
| 切片数 | 36（固定） | 调用次数多，每次都有进入/退出 + 打包开销 |
| M = n_tiles | 4 … 3136 | 小空间形状 M 极小（7² 图像只有 **4** 个 tile） |
| N = OC | 16 … 512 | 小 OC 时 N 不足一个向量宽度 |
| K = IC | 16 … 2048 | 小 IC 时 K 极短，流水线填不满 |

KML/arm_gemm 的通用内核为「大矩阵 + 多线程」优化：它们按 N/M 分块、每块重新打包
B 操作数、靠 K 维深度摊薄固定开销。在 Winograd 的「36 次小切片」形态下，
**K 短、M 小、调用密**，固定开销占比被放大。基线实测：t1 下这类小切片的有效
GEMM 吞吐只有**几十 GFLOPS**，而单核 SME `fmopa` 探针能到 **~2 TFLOPS/核**（4-tile 循环）。

因此目标不是「把 GEMM 写得更快」，而是**换一种与矩阵形态匹配的执行模型**：

- SME 的 ZA 是 **64×64 fp32** 的二维累加器（每 tile 16 KB，4 tile 共 64 KB），
  一条 `fmopa` 完成 64×64 外积的 1/16（全 ZA 需 16 条）；我们的 4-tile 版本一次
  `smstart…smstop` 内做 **IC × 4** 条 `fmopa`，即 IC × 4 × 256 次 FMA。
- K 维（IC）正好是外积的「深度」方向，**K 再短也不影响 tile 利用率**。
- 输出直接是 ZA 的二维布局，可一次性 `str za` 掉进目标内存。

## 2. 硬件与指令语义（本机标定结果）

### 2.1 前提寄存器

| 资源 | 规模 | 说明 |
|---|---|---|
| `ZA0..ZA3` | 每个 64×64 × fp32 = 16 KB | SME fp32 外积累加器 |
| Z 寄存器 | z0–z31，VL = 16 float（SVE-512） | 64 B / 寄存器 |
| 谓词 | p0–p15 | `fmopa` 用 `pN/m` 做行列掩码 |
| 模式 | `PSTATE.SM` / `PSTATE.ZA` | `smstart` / `smstop` 切换流式模式与 ZA |

本机 CPU 特性含 **`smef32f32`**（fp32 外积），`grep -m1 Features /proc/cpuinfo` 可见。

### 2.2 FMOPA 编码与语义

```
fmopa zaA.s, pM/m, pN/m, Zm.s, Zn.s
    →  zaA[row][col] += (pM[row] ? Zm[row] : 0) · (pN[col] ? Zn[col] : 0)
```

编码公式（用 5 组已知正确样本反推并逐位验证）：

```
inst = 0x8080b400 | (Zm << 16) | (Zn << 5) | Za
```

> 语义方向要特别注意：**`Zn` 是第一个列出的向量 → 映射到列侧（N 维）**，
> `Zm` 映射到行侧（M 维）。这一条弄反会让输出变成转置，且在小形状上不易察觉。

### 2.3 ZA 布局标定：为什么可以「drain 即写回」

用 K=1 的探针（每个 lane 填可区分的常数，执行 4 条 `fmopa`，再逐 slice `str za` dump）
得到本机约定：

```
str za[wS, #0], [addr]      // S = slice 选择寄存器，取值 v
  → 把 za[v & 3] 的「第 (v >> 2) 列」按 64 B（16 个 fp32）沿 Zm 行方向写到 addr
```

- **GEMM 路径采用的约定**：`slice 编号 v → za[v & 3] 的第 (v >> 2) 列`，
  按 64 B（16 个 fp32）沿 Zm 行方向写出。该约定由独立微内核探针做**逐元素精确比对**
  验证（`max |diff| = 0`），因此 GEMM 只依赖「写」侧，不依赖任何读回约定。
- 早期探针曾记录「slot 与物理列存在置换」，那是 **`mova` 读回**路径的约定；
  GEMM 内核不使用 `mova`，故不受该置换影响。若后续要改成「先读回 ZA 再处理」，
  必须重新标定读侧映射。
- 因此可以自由约定「ZA 行 ↔ 业务维度」与「ZA 列 ↔ 业务维度」的含义，无需后处理置换。

`str za` 的 slice 选择寄存器**编码上只有 2 bit，只能是 w12–w15**；若用其它寄存器
（例如 `%x[vv]` 被分配到 x14），GNU as 会静默插入一条 `mov x15, x14`，再编码
`str za[w15]`。这条 fixup 必须知道，否则会误判为「寄存器被莫名改写」。

## 3. 设计

### 3.1 操作数角色分配

```
ZA 行 (Zm)  = 16 个 OC          ← B 操作数（V）沿 IC 取一个向量的 16 个 OC
ZA 列 (Zn)  = 16 个 tile        ← A 操作数（U）沿 IC 取一个向量的 16 个 tile
za0..za3    = 4 个连续的 16-OC 块 → 一个 window 覆盖 16 tile × 64 OC
```

选择理由：

1. **drain 天然对齐输出布局**。`M_buf` 是行主序 `[ts][tile][oc]`，一行是
   `n_tiles × OC`，其中 OC 连续。`str za` 一次写 16 个连续 OC（64 B），
   所以每个 slice 恰好落在某一行的一段上——**零 shuffle、零转置**。
   若反过来（OC 在列、tile 在行），drain 出来的数据是跨行的，必然要做转置。
2. **tile 维天然分块**。`n_tiles` 恰好是 16 的倍数时最好（14²→16、64²→256、
   112²→784、160²→1600）；否则会有一个不满的尾组：
   `20²→25`（两组，尾组 9/16）、`40²→100`（七组，尾组 4/16）、
   **`28²→49`（四组，尾组只有 1 个 tile，利用率 6%）**——后者是 SME 在 28² 族
   落后的主因。`7²→4`（只有 4 个 tile，利用率 25%）却能赢，因为 K 极长、
   KML 在 M=4 时效率更低（见 §5）。
   尾块统一走 `stage[16*64]` 暂存后按有效前缀拷贝，成本可忽略。
3. **OC 维一次吃 64 个**。4 个 ZA tile 并行累加，`smstart/smstop` 与 K 循环
   的固定开销被 4 倍摊薄。

### 3.2 操作数打包（把「转置」搬到源头，且只做一次）

微内核要求两个操作数都是 **K 主序**（同一个 k 上，16 个 lane 连续）：

```
A: Ug[ts][g][k][0..15]      // 16 个 tile 在同一个 ic 上的 U 值连续
B: Vkt[ts][k][0..OC64-1]    // OC64 个 OC 在同一个 ic 上的 V 值连续，OC 向上补到 64
```

- `Vkt`（B 操作数）**与 V 一起在权重缓存条目发布时打包**（`VCacheEntry::vkt`），
  同一把锁内完成，读者不会看到半成品；缓存未命中时才用 `sVkt` scratch 现打包。
  推理场景权重恒定 → **每次调用零 B 打包成本**。
- `Ug`（A 操作数）由 **Phase-1 的 16-tile 组路径**直接产出：输入变换结果先写进
  按组暂存的 `Ust[ts][i][ic]`（i<16），再由 `pack_ug_group` 用 SVE gather
  （`svld1_gather_u32index_f32`）做 16×16 块转置写入 `Ug`。
  行主序的 `U` 在 SME 路径上**完全不落地**，所以没有额外的 scatter 遍历。

> 为什么不让输入变换直接写 `Ug`？变换 kernel 的输出天然是
> `[ti][tj][ic]`（6×6 空间 × 通道连续）。要写 K 主序需要 16 个 tile 同时在手，
> 而变换是按 tile 独立调用的。当前实现选择「按组暂存 + 一次块转置」，
> 代价约等于一次 U 大小的读写，换来实现简单且对 SVE 变换零侵入。

### 3.3 微内核 `gemm_window`

```asm
smstart                        ; 打开 SM + ZA
ptrue  p0.s
zero   {za0.s, za1.s, za2.s, za3.s}
1:                             ; K 循环，每次前进 1 个 ic
ld1w   {z16.s}, p0/z, [x9]           ; A: 16 tiles @ k
ld1w   {z17.s}, p0/z, [x10]          ; B: OC 块 0 @ k
ld1w   {z18.s}, p0/z, [x10, #1, MUL VL]
ld1w   {z19.s}, p0/z, [x10, #2, MUL VL]
ld1w   {z20.s}, p0/z, [x10, #3, MUL VL]
fmopa  za0.s, p0/m, p0/m, z16.s, z17.s
fmopa  za1.s, p0/m, p0/m, z16.s, z18.s
fmopa  za2.s, p0/m, p0/m, z16.s, z19.s
fmopa  za3.s, p0/m, p0/m, z16.s, z20.s
add    x9, x9, #64              ; A 的 k 步进 64 B（16 tile）
add    x10, x10, bstep          ; B 的 k 步进 = OC64 × 4 B
cmp/add/b.lt
```

- **算术强度**：每轮 4 条 `fmopa` = 4×256 = 1024 FMA = 2048 FLOP，配 5 次 64 B 加载
  → 6.4 FLOP/byte，明显高于通用内核在这类小矩阵上的表现。
- **drain**：64 次 `str za[wS,#0],[addr]`（v = 0..63 编码 slice/列），按
  `tile = v>>2`、`oc-block = v&3` 计算目标地址；若该 16-OC 块越界（`OC` 不是 16 的
  倍数），改写 `stage`，由调用方按有效前缀拷贝。
- `smstart/smstop` **每个 window 一次**，不是每个 k 一次。

### 3.4 流水线集成

```
Phase 1 (输入变换)   每 16 tile 一组：
                     extract & transform → Ust[ts][i][ic]
                     pack_ug_group (16×16 块转置) → Ug[ts][g][k][t]
Phase 2 (GEMM)       gemm_phase:
                       omp for (ts) → 每组 tile × 每 64 OC → gemm_window
                       （末尾自带 barrier）
Phase 3 (输出变换)   与 KML/arm_gemm 路径完全一致，未改动
```

- 编译开关：`#if defined(__ARM_FEATURE_SME)`；运行时开关 `WINO_GEMM=sme`
  （`wino_sme::requested()` 缓存环境变量查询）。
- `OC < 16` 时自动退回默认后端（`wino_sme::active()`）。
- `WINO_V_CACHE=0` 可关闭权重缓存（连同 `vkt` 一起每次重打包）。
- 默认路径（不设 `WINO_GEMM`）**完全不变**，SME 代码不参与任何计算。

## 5. 性能

> **测量条件**：本机 608 核毕昇环境，GCC 12.3.1 `-O2`；同一二进制、同一进程内仅切换
> 环境变量（`WINO_GEMM=sme` vs 默认 KML）。t1 用 `taskset -c 3` 固定单核；
> t16 用 `OMP_PROC_BIND=close OMP_PLACES=cores` 绑定 16 核（同一 NUMA 节点）。
> warmup 2 + repeats 3，取最好一次。
> 全部用 `--sve`：变换走 SVE，**只对比 GEMM 后端差异**，不掺 SME 变换的影响。

### 5.1 汇总

| 线程 | SME 合计 | KML 合计 | 合计比 ΣSME/ΣKML | 几何平均 speedup | 算数平均 speedup | 中位数 speedup | SME 胜出 |
|---|---|---|---|---|---|---|---|
| t1（固定单核） | 3317.9 ms | 3403.3 ms | **0.975**（SME 快 2.5%） | 1.007 | 1.060 | 1.014 | 31/59 |
| t16（绑 16 核） | 345.9 ms | 386.3 ms | **0.896**（SME 快 10.4%） | 0.901 | 0.989 | 1.022 | 32/59 |

> speedup 统一取 **KML / SME**（>1 表示 SME 快）；合计比取 **ΣSME / ΣKML**（<1 表示 SME 快）。
> 两次独立重复的波动：t1 合计差异 <0.3%，t16 <2.5%（见 §5.6 口径说明）。

**四种口径在 t16 上给出方向相反的结论**，这不是错误，而是分布本身是双峰的：

- **合计比 0.896**：整套 59 形状的总耗时 SME 少 10.4%——大形状（160²/224² 族）的收益压过了小形状的损失。
- **几何平均 0.901**：一个「典型形状」上 SME 慢约 10%——少数形状被拖到 0.29–0.45x，在 log 尺度上拉低均值。
- **算数平均 0.989**：随机抽一个形状，比值期望接近持平（算数平均被大加速比抬高，故比几何平均乐观）。
- **中位数 1.022**：一半形状 SME 更快，一半更慢——最抗离群值。

### 5.2 几何平均 vs 算数平均：该关心哪个

| 指标 | 定义 | 回答的问题 | 特性 |
|---|---|---|---|
| **合计时间比** | ΣtA / ΣtB | 跑完这一整套用例要多久 | 按真实耗时加权，被大形状主导；**直接对应吞吐** |
| **几何平均** speedup | `exp(mean(log(tB/tA)))` | 一个典型形状上快多少 | 比值尺度正确；**换方向结论不变**；抗极端值；论文/SPEC 通用口径 |
| **算数平均** speedup | `mean(tB/tA)` | 随机抽一个形状的期望比值 | **换方向会变**；被大比值抬高；AM ≥ GM 恒成立 |
| **中位数** speedup | `median(tB/tA)` | 一半形状快于/慢于多少 | 最抗离群；适合双峰分布 |

三条必须知道的性质：

1. **几何平均对方向对称，算数平均不对称**。`geomean(r) = 1 / geomean(1/r)` 恒成立，
   所以「A 比 B 快几倍」和「B 比 A 慢几倍」用几何平均换算完全一致；
   算数平均做不到——本表 t16 的算数平均（speedup）是 0.989，把比值反过来
   （SME/KML）再算算数平均是 **1.230**，乘积 1.22 ≠ 1。
   **因此报算数平均时必须写清方向**，否则数字不可复现。
2. **AM ≥ GM 恒成立**（AM-GM 不等式）。对「加速比」用算数平均总是更好看，
   这是它常见的误用动机：同一份数据，几何平均 1.99x、算数平均 2.17x（见
   `docs/final_benchmark_bfd6b1e.md` 的 OpenBLAS 对照）。
3. **只有合计时间比直接回答「这套负载要跑多久」**，但它会被最慢/最大的几个形状主导；
   反过来，几何平均对每个形状等权，会让「10 个微小形状」和「10 个大形状」同权。

**建议的读法（也是本文档的约定）**：

| 问题 | 看哪个 |
|---|---|
| 这套 59 层网络端到端能快多少 | **合计时间比**（吞吐视角） |
| 典型形状上快多少 / 与别的实现可比 | **几何平均**（等权、可跨报告比较） |
| 有没有异常形状 / 分布是不是双峰 | **中位数 + 逐形状表** |
| 其它 | 算数平均只作辅助，且**必须标注方向** |

> 补充关系：speedup 的**调和平均**恒等于「SME/KML 比值的算数平均」的倒数
> （`HM(tB/tA) = 1 / mean(tA/tB)`）。本文档不单独列它，避免指标泛滥。

### 5.5 胜负模式与原因

**SME 明显胜出的区间（t1 最高 2.2x，t16 最高 1.8x）**

| 类型 | 例子（t1） | 比值 | 原因 |
|---|---|---|---|
| 小空间 + 深通道 | #15/16 `512,7²`、#19 `1024,14²`、#20 `2048,7²` | **0.45–0.48x** | `7²→4 tiles`、`14²→16 tiles`（一组正好）；K=512–2048 极长，外积深度利用充分。KML 在此区间只有 20–22 GFLOPS（M 太小，分块填不满），SME 即使只用 4/16 lane 也赢 |
| 大空间 + 小 IC | #21/22 `64,224²`、#55–57 `48…192,160²` | 0.75–0.93x | tile 数多（56²=784、160²=6400），ZN 一直满载；IC 小使 KML 的 K 维太短 |
| 大空间 + 中等 IC（t16） | #21/22、#54–58 | 0.55–0.84x | 16 线程下 tile 组足够多，`omp for (ts)` + 组内窗口填充良好 |

**SME 落后的区间（t1 最高 2.0x，t16 最高 3.45x）**

| 类型 | 例子 | 比值 | 原因 |
|---|---|---|---|
| 小空间 + 大 OC | #27/28 `512,28²`、#42–46 `48…384,20²` | 1.36–2.0x | `28²→49`（尾组仅 1 tile，ZN 利用率 6%）、`20²→25`（尾组 9/16）；OC 大 → 窗口数多，每个窗口固定 drain 64 个 slice，浪费与 K 无关 |
| t16 下 tile 数少的形状 | #3/6/8 `192…768,20²` | 1.94–3.45x | 并行度只来自 36 个 ts（组内 2 组），16 线程争抢；KML 的 GEMM 在 N=96–192 时并行效率更高 |
| 极小形状 | #39 `8,16²` | — | `OC<16` 自动回退默认后端，属噪声 |

**结论**：SME 的优势来自「**不依赖 M 维规模**」——M（tile 数）再小也不损失外积利用率，
因此恰好命中通用 BLAS 最不擅长的「小 M、长 K」区间；劣势来自 **ZN 方向只有 16 个 lane**
与 **每窗口固定 64 次 drain**，在「tile 数不是 16 的倍数」或「OC 很大」时摊不薄。

### 5.6 测量口径说明（重要）

1. **必须绑核**。不绑核时的合计值（同一二进制、同一用例集）：

   | 口径 | SME 合计 | KML 合计 | 表观结论 |
   |---|---|---|---|
   | t1 不绑核 | 3132 / 3208 ms | 2894 / 2481 ms | SME 慢 8–29% |
   | t1 绑核（本文） | 3318 / 3310 ms | 3403 / 3390 ms | SME 快 2.5% |
   | t16 不绑核 | 387 / **558** ms | 321 / 268 ms | SME 慢 21–108% |
   | t16 绑核（本文） | 346 / 341 ms | 386 / 383 ms | **SME 快 10%** |

   不绑核时结论会完全翻转（t16 甚至相差 2x）。原因：16 线程散落在不同 NUMA
   节点时，SME 路径的大块打包缓冲（`Ug`/`Vkt`/`M`）产生大量远程访问；
   同时该机器存在跨作业/跨调度的性能态漂移。**本文所有数字均为绑核结果。**
2. **V 缓存上限 24 条**，而用例集有 59 个不同形状。缓存满后不再新增条目
   （无淘汰策略），因此 **第 25–59 号形状每次调用都会重新打包 `Vkt`**。
   实测这笔开销在 t1 为总时间的 0.3%–15%（大 OC 小空间形状最重），t16 因并行化
   可忽略。真实推理中同一层会反复调用，缓存命中，故此处对 SME 略偏保守。
3. **`--sve` 与 `--sme` 的区别**：两者只影响变换路径；GEMM 后端由 `WINO_GEMM` 决定，
   互相独立。本文统一用 `--sve`，避免把 SME 输出变换的差异混进来。

## 6. 关键 bug 复盘：`smstart`/`smstop` 会摧毁调用者的 callee-saved 向量寄存器

这是本内核开发中最贵的一课，现象极具误导性。

### 6.1 现象

- 数据**完全正确**（verify 通过、微内核自检 max diff = 0），但**计时输出 `inf`**。
- `std::chrono` 的 `duration` 转换（`ticks * 1e6 / freq`）返回 `inf`；
  原始 tick 差正确（~7.8 ms），`scvtf`（int→double）也正常。
- `-O0` 构建正常，`-O1`/`-O2` 必现（GCC 与 clang 都中招）。
- 独立小程序 `minwin.cpp`（同样的 asm + main）**不复现**。
- `FPCR`/`FPSR` 前后都没变。
- 把 window 体换成只有 `smstart; smstop` 两条指令，**仍然复现**。

### 6.2 定位过程（有效的那一步）

在测试程序里直接读 `v11`（callee-saved 的 128 bit 寄存器，编译器把常量 `1e6`
放在 `d11` 里）：

```
KML 对照组：  call 前 v11 = 0x412e848000000000  ✅
SME 组：      第一次调用「之前」的打印就已经是 0  ❌
```

即：**第一次 `winograd_convolution()` 返回时，调用者的 d11 已经被清零**。
`ms = ticks / 1e6` 变成 `x / 0` → `inf`。数据正确是因为算的是另一批寄存器。

### 6.3 根因

ARM ARM 规定：`smstart`/`smstop` 切换流式模式时，**所有 SVE 向量寄存器（z0–z31）
与所有谓词（p0–p15）都变为 UNPREDICTABLE**。而 AAPCS64 的 callee-saved 约定是
**d8–d15（z8–z15 的低 64 bit）**。

内联 asm 的 clobber 列表当时只写了 `z16–z20`（caller-saved，本来就允许破坏）
和 `p0`。编译器因此**认为 z8–z15 在调用点之后仍然有效**，把活值留在里面；
`smstart/smstop` 一过，这些活值全废。

- `-O0` 不复现：所有值都落栈，没有跨调用的活跃向量寄存器。
- `minwin` 不复现：`main` 里没有 SVE 代码，也没有足够多的活跃 callee-saved 向量值。

### 6.4 修复

```c
: "memory", "cc",
  "x1", …, "x14",
  "d8", "d9", "d10", "d11", "d12", "d13", "d14", "d15",   // ★ 必须
  "z16", "z17", "z18", "z19", "z20",
  "p1", …, "p15",                                          // ★ 必须
  "p0"
```

**规则**：任何内含 `smstart`/`smstop` 的 inline asm，clobber 必须覆盖
`d8–d15` 与 `p1–p15`；只写自己「显式用到」的寄存器是不够的——模式切换本身
就会让它们全不可预测。

> 同类风险：`include/winograd_transforms_sme.hpp` 的 F(4,4) 输出变换 asm 使用
> z0–z31，若它被**真正作为函数调用**（而非内联）也会遇到同一问题。当前它总是
> 内联在 dispatch 内，编译器能看到 clobber 并保存/恢复；一旦改成 `noinline`
> 或跨 TU 调用，需要同样补齐 `d8–d15`。

## 8. 后续优化方向（按预期收益）

1. **消除 `Ust → Ug` 转置**：让 SVE 输入变换在「一组 16 tile」的粒度上直接写
   K 主序，省掉每组 36 × 16 × IC 的读写（当前约占 SME 路径可观比例，大 IC 尤甚）。
2. **OC 尾块专用 tile 数**：`OC=96` 时 4-tile × 2 窗 = 8 个 16-OC 块（浪费 2 块）；
   改成 3-tile × 2 窗正好 6 块，可省 25% 的 `fmopa`。
3. **按形状混合调度**：SME 在「小空间 + 深通道」（7²/14²）与「大空间 + 中/小 IC」
   （160²/224²）两块区间稳定胜出；在「小空间 + 大 IC/大 OC」（20²/28² 族）落后。
   可加形状判据（`n_tiles` 是否接近 16 的倍数、`OC` 对 64 的填充率、`IC` 大小）
   自动选后端，把两边的优势区间拼起来。
4. **多 window 流水**：当前一个 window 内 drain 完再进下一个，`smstop` 期间
   无法继续累加；可考虑把两个 group 的 drain 与下一个 group 的 K 循环交错。
