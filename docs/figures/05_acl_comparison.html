⑤ 与 ACL 的差异与优势

同一套数学，两种工程哲学：ACL 用「手写内核 + 形状自适应」，本项目用「泛型内核 + 系统级取舍」。

汇报时先讲这一页，后面的差异才站得住：数学层面 100% 同源，差别全在工程实现与调度策略。

03六条诚实的差距

建议汇报时主动说 K1 与 K4 —— 主动暴露短板的报告更可信，而且这两条都有明确补法。

#差距具体补法
K1 单 kernel 效率transform_1d_sve 约 52 cyc/向量操作（理想 ~2）；ACL 全展开、寄存器驻留 F(4,4) 专用展开内核，预期变换 −30~50%
K2 多两趟内存往返输入 scatter 6% + 输出 gather 15%（Case 0 串行计时） 变换直接写 GEMM 序（tile-major 已被实测证伪：−14%/−16%）
K3 小形状无 hybrid 退路batch=1、IC≤128、spatial≤56² 慢 0.09–0.91x im2col + arm_gemm 直接卷积路径
K4 SME GEMM 未与 ACL 的 SME 内核同机对打构建时用 filter="sve_" 强制了 SVE 内核 WINO_GEMM_FILTER="" 放开，同作业 A/B
K5 覆盖面窄仅 fp32、2D、3×3、unit stride 有意取舍

04同算法 PK 的三种口径

oneDNN 的三列回答三个不同问题，不能混用。

对照列oneDNN 算法回答的问题结果
e2e_auto自动（40 wino:acl + 19 brgconv）我们比 oneDNN 最优选择快还是慢 大形状快 1.1–2.8x；小形状慢 0.09–0.91x
e2e_wino强制 wino:acl同样做 Winograd，谁更快 全部 1.15–9.5x
benchdnn_winowino:acl（driver 口径）换一个 driver 复核 与 e2e_wino 一致，互证
口径提醒：ACL 选 F(4,4) 还是 F(2,2) 取决于它的构建是否启用 SME。 集群侧 oneDNN 的实际选中项未从日志确认（历史文档记为「疑似 F(2,2)」）， 因此 1.15–9.5x 应读作「我们的 F(4,4) vs 对方当时的实际选择」。
