⑦ 测量方法与判读口径

怎么证明「快」不是测量假象：同作业 A/B、绑核、四种平均、方向约定与已知陷阱。

01第一原则：比较必须在同一作业内

跨作业的毫秒数一律作废——不是保守，是实测有 3–7x 的性能态差。

集群 920F 的实测：同一份二进制、同一个 shape，在 node03 的不同 sbatch 作业里可以读出 321.9 / 490.7 / 690.0 ms。任何「上次跑的是 X，这次是 Y」的对比都不可用。 本仓库所有集群结论都产自 sbatch -w node03 --exclusive --wrap="bash tools/onednn/ab_onednn.sh" 这一个作业内的交替测量。

02第二个前提：绑核（本机）

不绑核的 t16 数字会漂到结论翻转。

本机 608 核 / 32 NUMA、无调度器。OpenMP 线程若被放到不同 NUMA 节点， 内存访问代价随放置变化，SME 与 KML 的对比会失真。

档位绑核方式不绑核的后果
t1taskset -c 3单线程被迁移 → 缓存全失效，读数抖动 ±20%
t16OMP_PROC_BIND=close OMP_PLACES=cores SME 合计在 387–558 ms 间漂移，结论翻转成「SME 慢 2 倍」；绑核后两次重复差异 < 2.5%
协议：SME vs KML 的每一条数字都出自绑核运行； 每个配置重复两次，取同一作业内的读数。集群与本机是两套机器，毫秒数不可跨机比较， 只能各自纵向解读。

03四种平均：回答四个不同的问题

同一个比较会给出四个不同的数——差异本身也是信息。

vs OpenBLAS（集群，t16）

中位数 1.77 < 几何 1.99 < 算数 2.17 < 合计 2.50： 说明少数极大加速比（大形状）拉高了合计与算数平均，分布右偏。

SME vs KML（本机，t16 绑核）

合计 1.117 与几何 0.901 同时成立： SME 赢的是少数大 shape（省下的绝对时间多），输的是小空间大 IC（数量多）。 这正是「必须同时报四个数」的典型场景。

04方向约定：比值的分子分母写清楚

方向写反会让结论完全相反，这是本仓库踩过的坑。

对照定义>1 的含义仓库字段
vs OpenBLASOpenBLAS / 本项目>1 = 我们更快total_speedup
SME vs KML · 合计SME / KML<1 = SME 更快total_ratio
SME vs KML · 逐形状KML / SME>1 = SME 更快图表柱高
同一个「合计」有两套写法： 时间比 SME/KML = 0.896 与加速比 KML/SME = 1.117 描述的是同一件事。 生成脚本里两个字段同时存在（total_ratio / total_speedup）， 就是为了避免显示方向出错。
